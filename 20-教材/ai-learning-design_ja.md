## 1. 教育哲学（前提として最重視するもの）

本プロジェクトの学習支援は、一貫した軸の上に立つ。AIアシスト方針はこの軸から逆算する。

```text
言語力 > 技術力
  読解力・聴解力・言語化力の育成が、技術力育成より優位にある。
  「言語化できること」が最重視される（最も難しいが、最も重要）。

構築主義
  文法を一から演習で積む方式の「正反対」。
  ある程度複雑なサンプルアプリをまず動かす → 改造する
  → その過程で文法を掴む。

判断履歴の重視
  コードの束や zip ではなく、設計記録1枚を渡す。
  「なぜそうしたか」を最重視する。
```

これらを通す学習の流れは、**観察 → 痕跡を残す → 言語化 → 比較・検証 → 自己判定 → 共有・再検証**。
観察は言語化の前提であり、まだ言葉にならない違いを、言語化できないという理由で捨てない。学習支援の目的は
生徒を教師が評価しやすくすることではなく、生徒自身が「何を観察し、何を根拠に、できた／まだできていないと
判断すればよいか」を獲得することに置く。

WireScopeは、この順序を通信観察へ投影する。現在のread-only observerから、見る→選んで見る・比べるへ進み、
将来「つつく」を加える場合もbrowserへcontrol能力を与えず、独立console sourceを増員する。capabilityと
学習段階の接続は`2026-08-10-03`、技術正本は
[WireScope deployment設計](../15-wirescope/wirescope-deployment-design_ja.md)を参照する。

## 2. 中心原理: なぜAIアシストとこの哲学が噛み合うのか

AIアシストは上記3軸すべてと**構造的に一致する**。これは偶然ではなく、設計の土台。

```text
言語力 ↔ AI へのプロンプトも生成物の評価も、すべて言語行為
  → AI 時代、言語力は「技術を動かす力」そのものになった。
  → 言語力を先に据えていたことが、図らずも最適解だった。

構築主義 ↔ AI は「複雑なサンプルを即座に用意する」のが得意
  → 「まず動く複雑なものを与える」コストが激減。
  → 構築主義の最大の難点（良質教材の用意・学習者が複雑さに溺れるリスク）を
    AI が生成と伴走で解く。
  → AI が構築主義を初めて実用的にした。

判断履歴 ↔ AI が生成を肩代わりした後、人間に残るのは判断
  → 「なぜそうしたか」こそ人間の領分、という構造が一致。
```

## 3. 「細部把握の必要性」への回答（逆説）

「AI 時代に細部を全て把握する必要があるか」は、2つの異なる問いの混同。

| 問い | AI の肩代わり | 必要性 |
| ------ | -------------- | -------- |
| コードを生成・記述するための細部把握 | できる | 劇的に低下 |
| 生成物を判断・検証・統合するための細部把握 | できない | むしろ上昇 |

**消えるのは「暗記・記述の労力」、消えないのは「判断のための足場」。** AI を使いこなす人ほど土台の理解が深く、AI に使われる人は判断できず生成物を鵜呑みにする。後者の価値（判断の足場）は希少化して上がる。

## 4. 設計原則（各プラットフォーム共通）

```text
AIにコードを生成させてよい。
ただし学習者は『なぜそうなるか』を言語化できること。
= 生成は任せ、判断は学習者が握る。
```

**補足（誤読防止）**：これは「AI に生成させない」ではない。生成はむしろ委譲し歓迎する（§2＝AI が構築主義を初めて実用的にした、§5 Python 層＝AI の出番は最大）。握るのは判断・検証・統合・言語化。後述の「答えを手渡さず問い返す」（本節の壁打ち・[debug-session-design]）は**チューター対話の局所設計**であって、生成そのものの禁止ではない。両者を潰すと「生成は任せ、判断を握る」が「生成させない」に反転する。

これは「判断履歴重視」哲学の学習版。各層で「AI に渡してよい部分」と「学習者が握るべき部分」の境界が、学習目的によって異なる位置にある。**一本の方針で全層を貫こうとすると失敗する。**

**補足（2026-06-30）: 全ては投影で扱う。** 正本は密な SSOT に置き、学習者・貢献者・開発者が受け取るものは、
言語、作業対象、現在の熟達度、利用している LLM / サーフェスに合わせてその場で投影する。同じ人でも、ある対象では
プロ、別の対象では入門者になりうるため、適応単位は「人」ではなく「テーマ × 現在地 × 作業」。コーディングも
LLM アシスト前提なので、教材・開発・OSS 貢献・ナレッジ運用は分断せず、同じ投影原理でつながる。

### 補助原則: 「AIアシストに振りすぎない」

- エージェント型 AI は便利すぎて、学習者から主体性を奪いやすい（主体が AI に移る）。
- インライン補完型（従来の Copilot 的）は「学習者が書こうとしている途中の補助」で、主体は学習者に残る。構築主義・言語化と相性が良い。
- → 教育用途では、デフォルトで全部を AI に振らない設計を意図的に行う。どこまで任せるかを教材ごとに設計する。

### AI を「言語化の壁打ち相手」として使う

AI は答えを出す道具としてだけでなく、**言語化を引き出す個別チューター**として使える。

```text
育てる使い方 ↔ 奪う使い方
  「なぜ?と問い返す AI」 ↔ 「答えを即座に出す AI」
  同じツールが、設計次第で正反対の効果を持つ。
```

「生成は任せ、判断は握る」原則が、この分岐の防波堤になる。とくに低年齢層では言語化のハードルが高いため、「問い返す」対話設計が要となる。

### 観察から自己判定までを支える

「なんか動かない」は誤った報告ではなく、まだ分解されていない観察である。学習者へ最初から原因説明や長い文章を
要求せず、次の順で足場を置く。

```text
何が起きると思ったか
  ↓
実際に何が見えたか
  ↓
どこが違うと気づいたか
  ↓
その違いを残す（スクリーンショット・ログ・値・短いメモ）
  ↓
次に何を見れば切り分けられるか
  ↓
何を根拠に、できた／まだできていないと判断したか
```

スクリーンショット等は文章を書けないときの劣った代替ではなく、**解釈を要求する前に観測を保存する低い入口**。
「言語要求を下げる」ことと「思考要求を下げる」ことを混同しない。AI は原因や点数を先に返す評価者ではなく、
「何が見えたか」「何が違ったか」「次に何を見るか」を問い、観察の切り出しと言語化を助ける鏡として使う。

自己評価は感想や自己採点ではない。学習者が作品について主張し、根拠となる観察を選び、未確認部分を区別できる
ことを指す。教師・AI が正誤を返し続けるのでなく、正しさの判定権と検証方法を学習者へ返す。

### 創造性を支える制約

自由度は、それだけでは創造性を生まない。現在のスコープを把握し、外枠を見る／細部へ潜る／別のスコープへ移る／
再接続する、という可逆な操作を支える適度な制約を置く。教師が進行・評価を揃えるための管理的制約と、学習者が
注意を配分して探索・深化するための創造的制約を区別する。

## 5. 各層のAIアシスト最適点

学習目的が境界を決める。各層で位置が論理的に定まる。

### Scratch（低年齢・コーディングを楽しむ）

- 目的: 達成の喜び、プログラミング的思考。
- AI の出番: コーディングには**限定的**（コーディング自体が目的のため）。アイデア整理には使う。
- 現状: 言語化ハードルが高い年齢層 → 動画・スライド・実演の比率が高い（これは正しい）。
- 位置づけ: Python 導入の前段階。mod 方式の Scratch マイクラリモコンを使用。箱庭サーバー利用が可能になれば、さらに年齢層を下げられる目論見。
- カリキュラムの言語化・テキスト化を急ぐ方針。

### Python 入門（構築主義の本丸 / AI と最も噛み合う）

- 目的: 複雑なサンプルを動かし改造しながら文法を掴む。
- AI の出番: **最大**。範囲を狭く設定でき、生成コードと自分のコードの差分を読め、完全理解が現実的。
- 条件が揃う唯一の層: 構築主義 × 狭い範囲 × 差分の可読性。
- → **AIアシスト導入版を最優先で用意する**。
- PythonAPI / クライアントは Python 側の良い教材になる。

### mod 開発（上級・完全に別メニュー）

- 目的: プラットフォーム差の判断力 + 実装力。
- AI の出番: フル活用、人間は設計判断・検証・統合に集中（プロジェクト主導者自身のワークフローと同じ）。
- [platform-design](../11-plugin/platform-design_ja.md) の3ステップ（Forge 1.20.1 / Forge 1.21.1 / NeoForge 1.21.1 を辿って差分を体感）はこのトラック。

### Java版 / Unity 連携（将来）

- Java: プラットフォーム差を判断できる足場 + 実装力。AI フル活用、人間は設計判断。
- Unity: 統合・橋渡しの設計理解。AI は結合コードを生成、人間はアーキテクチャを握る。

## 6. mod開発カリキュラムとAIの関係（順序の判断）

対象は上級者（マイクラリモコンの 8〜80 歳ターゲットとは別層）。

### 決定: Architectury に「早く寄せない」

- 現行の3ステップ（Forge 1.20.1 → Forge 1.21.1 → NeoForge 1.21.1）は、**差分を手で体感する**教育設計。
- Architectury は差分を隠蔽する仕組み（@ExpectPlatform / 共通 API）。差分を体感する前に被せると、「何を抽象化しているか分からないまま抽象化を使う」状態になり、教育価値が失われる。
- 順序を守る:

  ```text
  Step 1: 3ステップで差分を手で味わう（縦=MC版差、横=ローダー差）
  Step 2: その後 Architectury 導入「さっき書き分けた違いを、こう吸収できる」
  ```

- アナロジー: 生 DOM を触ってから React、アセンブリを触ってから C 言語。

### AI 時代における3ステップの正当性（むしろ増す）

- 従来の目的「差分を覚えて手で書く」は半分陳腐化（手で書く部分は AI がやる）。
- AI 時代の目的「差分の存在と意味を判断できる足場を作る」は必須化。
- → 力点を「記述の習得」から「差分の意味理解」へ移す。各ステップで AI に生成させ「なぜ Forge と NeoForge で違うか」を読み解く演習にしてもよい。手を動かす対象が「タイピング」から「判断」へ。

### Forge 1.21.1 の扱い

- 実用ではほぼ選ばれないが、**教材としては残す価値あり**（2軸の差分を綺麗に分離して見せられる: Forge 1.20.1→1.21.1 で同ローダーの MC 版差、Forge 1.21.1→NeoForge 1.21.1 で同 MC のローダー差）。Architectury が何を吸収するかの伏線にもなる。

## 7. 導入の段階論

AI 側の進化が速く（この1年で大きく変化）、急ぐ必要がある。一方、生徒の反応・教材の浸透力／定着力は読みきれないため、実データを見ながら方向性を出す。

```text
Phase 1: 無料・ブラウザベースの AI 利用から入る
         → AI との壁打ちで言語力養成
         → 生徒が AI をどう使うか、どこで詰まるか、
           言語化がどこで起き/起きないかの実データを収集

Phase 2: Phase 1 の観察を仕様に変換し、組み込み型 AI（方向B）を設計
         → 「問い返す振る舞い」を実データから逆算
         → 最初の実験場は [debug-session-design](../13-scratch-client/debug-session-design_ja.md) のブラウザセッション画面
```

組み込み型を「いきなり完成形で作る」のではなく、「ブラウザ期の観察を設計仕様に変換する」。これ自体が構築主義（まず動かす→観察→改造）の実践。

### 実装形態の2方向

| 方向 | 内容 | 利点 | 欠点 |
| ------ | ------ | ------ | ------ |
| A | 外部 LLM（ブラウザ）の使い方を教える | 実世界ツールそのもの／実装コストゼロ | 「答えを出させる」誘惑を制御しにくい |
| B | 教材に組み込んだ AI（範囲・振る舞いを制御） | 「問い返す／答えを出さない」を設計に埋め込める／哲学を直接反映 | 実装が必要 |

→ **「まず A で導入、設計が固まったら B へ」**の段階論を採用。B は美しいが時間がかかる。

## 8. ツール環境の論点

### ツールチェーン: uv 統一（Windows 必須環境ゆえ）

学習支援は Windows を外せない。従来の pyenv-win は新しい Python 版を取得できないメンテ停滞
状態（Issue #725）で、将来性が乏しい。uv は単一バイナリで Python 取得〜venv〜lock〜build〜
publish を一律化し、Python 版の取得・固定も内蔵して pyenv の役割を包含する。カリキュラム全体を
uv に統一する（決定 `2026-06-24-02` / 事実 `F-pyenv-win-stale`）。

  **【精密化 2026-07-17】** 測る対象を文章量や説明の巧さへ畳まず、観察から自己判定までの自立度として扱う。
  期待と実際を分けられるか、違いを見つけて痕跡を残せるか、次に見るものを選べるか、判断根拠と未確認部分を
  区別できるか、他者の問いを受けて判断を更新できるか、を観測候補とする。
- Java / Unity 層の具体化は将来。

## 10. 設計メモ（protocol b1 議論からの昇格・2026-06-27）

出典: claude.ai 設計議論 × ナレッジ突き合わせ 2026-06-26（DECISIONS `2026-06-27-02` / `2026-06-27-03` / `2026-06-27-05`・[wire-format-design](../10-protocol/wire-format-design_ja.md) §7）。catalog（[wire §7.2](../10-protocol/wire-format-design_ja.md)）連動で b2 以降に効く。

### AI 出力を catalog でハードゲート検証

「catalog に無い id を提案しない」は**プロンプト指示でなく validator で実現**する。AIが出したprotocol 22の`BlockSpec`（`block_id`＋`state` object）をcatalogの`states` schema・許容値と照合し、不正なら抑止して「現在のcatalogに無い」と表示する。プロンプト指示は漏れるがvalidatorは漏れない。Phase 2（埋め込み／制御AI、§7）・「AIに振りすぎない」補助原則（§4）・過剰依存対策に直結する。Python、Scratch、AI入力は同じschemaとfixtureを通し、一体文字列refのparseをclientごとに再実装しない（[block-value-design](../10-protocol/block-value-design_ja.md)、[wire §7.1](../10-protocol/wire-format-design_ja.md)）。

### 非言語 → getBlock 観察 → 言語化 の三段橋

パパート／レゴ／モンテッソーリ（control of error）の系譜。body-syntonicな理解を、**getBlockで世界を読み返す**（非言語→言語の変換器）ことを介して言語化に橋渡しする。核原則「AIにコード生成させてよい、ただし**なぜそうなるかを言語化できること**」（§1／§4）の非言語側の橋脚であり、§9最優先未決「言語化の伸びの測定」の観測材料にもなる。getBlockが完全修飾`block_id`とfull `state`を一つの構造化snapshotとして返す（[block-value-design](../10-protocol/block-value-design_ja.md)）ことで、「何であるか」と「どの状態か」を曖昧さなく読み返せる。

ScratchではMinecraft記法のStateText／BlockInfoTextを使い、Pythonのstate mappingと意味的に対応させる。
state名／値はja-Hira・jaと英語machine vocabularyを併記し、get→inspect→setと
`⟦mcr-error:<reason>⟧`による失敗分岐を比較教材にできる。詳細contractは
[Scratch block value投影設計](../13-scratch-client/scratch-block-value-projection-design_ja.md)を参照する。

## 11. Scratch 実行モデルと教育哲学（緑の旗の脱中心化・並列ビークル）

出典: claude.ai 設計セッション（Scratch 実行モデルの理解精密化）→ 確定搬送票 2026-07-04・repo 着地 2026-07-05。実行モデルの技術本体は [scratch-execution-model-design](../13-scratch-client/scratch-execution-model-design_ja.md)。項目3 が引く原典＝[なぜPythonか（2021-03-04・辻 直弘）](なぜPythonか.pdf)。以下は哲学本体（搬送票 verbatim）。

1. **「旗を前面に出さない」は工夫でなく意味論への忠実**。実行モデル精密化 項目4（手動ジェスチャとイベント語彙の分離）より、旗を特別扱いする教え方のほうが Scratch の実際から遠い。LLK にとっても旗は方便と読める設計証拠がある（ハット無しブロックのクリック実行・コンパイル/実行モード区別の不在＝tinkerability への深いコミットメント。Resnick & Rosenbaum "Designing for Tinkerability" 2013 系）。
2. **教育方針の二層化と順序**。作る側の思考では旗を脱中心化しつつ、公開する側の作法では旗は「見知らぬ観客のための入口規約」（共有・リミックス文化との整合）。カリキュラム順序＝最初は scaffold として旗を使い、イベントを学んだ後に「対等なイベントの一つ＋観客の入口規約」として再フレームする。
3. **2021「なぜPython」への時間軸接続**。「インタープリタ動作環境（iPython・REPL・Jupyter Notebook）が Scratch との共通性を高める／断片のチェック・組み合わせ・取替え＝試行錯誤が容易」（なぜPythonか 2021-03-04）の直観に、本精密化が実行モデルレベルの裏付けを与える。新説でなく **append-coherent な追記**として書く（2021→2026 の時間軸を残す）。Scratch と Python（Jupyter）は「入口→本格」の階段でなく「どちらも断片駆動でワールドを触る対等な乗り物」として収斂＝並列ビークル論の実行モデル版の裏付け。

### 並列ビークルの現行整理

Scratch を Python への一方向の踏み石として扱わない。両者は、同じ protocol と同じ world に別の認知入口から触れる並列の vehicle である。

- Scratch は、見える object と並行動作から因果を観察しやすい。
- Python は、生成・抽象化・再利用・検証を言語で組み立てやすい。
- Scratch で prototype を作り、Python で発展させ、結果を同じ world で比較できる。
- 並行性を Scratch 固有の魔法にせず、identity が main / substream を持つ共通 model へ写す。

土台の contract は `1 stream = 1 connection = 1 build state`（`2026-06-24-01`）。player identity が main stream と複数 substream を持てる方向を `2026-07-21-07` で起案している。Scratch stage / sprite / clone をどの stream へ写すかは b4 scope freeze 前に確定する未決であり、確定済みとして教材へ焼かない。

## 12. APIを最終成果にする3年間カリキュラム

コース名「アプリケーション開発講座」の到達点を、アプリを一つ完成させることだけに置かない。生徒が**APIを使う側から、設計し、sample applicationと文書を添えて他の開発者へ渡す側へ進む**ことを最終像にする。

中核文:

> Scratchで育った「作って動かす力」をPythonへ接続し、APIを使う側から、設計して他の開発者へ渡す側まで進む。

生徒は小学3年からScratchを経験している。Scratchを卒業前の踏み石として捨てず、同じ操作を複数の表現層で見る。

```text
Scratch block
  ↕
Python API call
  ↕
JSON-RPC frame（WireScope）
  ↕
McRemote plugin / Minecraft result
```

block設置の実行体験は、同じ`setBlock`／`setBlocks`をDEBUG／TRACE／FASTで切り替えて比較できる。
DEBUGはresponseとerrorを確認し、TRACEは成功後に呼出元だけを既定0.25秒待たせ、FASTは個別responseを
待たずに送る。Scratchは保存される`建築モードを [MODE] にする（TRACEの待ち時間 (秒)）`block、Pythonは
`setBuildMode()`を使い、アルゴリズム本体へmode別setterや`time.sleep()`を埋め込まない。ピラミッドの一段、
壁の一面等を一回の`setBlocks`にすれば、TRACEで構成過程を観察できる。TRACE delayは0〜2.0秒とし、
それより長い停止は通常の待機block／`sleep()`としてアルゴリズム上へ明示する。

FASTは成功を意味せず、server-side errorも個別には戻らない。完了確認は`connection.flush`に対応する
「送ったブロック設置が終わるまで待つ」またはPythonの`mc.flush()`を使い、状態確認は明示的なget系で行う。
WireScopeではnotificationを「送信済み・結果未確認」（`sent-unconfirmed`）、flushをbarrierとして読み、
syntheticな成功を教えない（決定`2026-08-20-03`／`2026-08-21-02`）。

3年間のprogressionは次を基準にする。

1. **APIを使う**: function、引数、戻り値、loop、座標、自動建築、errorを体験する。
2. **APIを組み合わせる**: module、data、test、再利用可能なwrapperを作る。
3. **APIを設計して共有する**: public surface、命名、error、sample application、test、README、GitHub presentationを完成する。

最終repositoryの標準骨格は、`README.md`、`pyproject.toml`、`src/`の生徒API、`examples/`のsample application、`tests/`とする。READMEは目的、install、最小例、API一覧、sample app、制約、発展案を説明し、発表は「何を作ったか」だけでなく「他の人がどう使えるか」を中心にする。

発表は完成品を披露して教師に評価される終端ではなく、学習者が期待・観察・違い・試行・判断根拠・未確認部分を
共同体へ開き、他者の問いによって自分の判断を再検証する工程とする。作品（何ができたか）・制作過程（何に気づき、
何を試したか）・判断（何を根拠に完成／未完成としたか）は一致しないため、一つの点数へ畳まない。

### 共通基盤と選択層

他学年・他教師と共通化するのはPythonの基礎、`uv`、repository、test、README、発表の土台である。McRemoteは選択層として載せ、全クラスの成立条件にしない。選択層が魅力的であれば生徒が自然にMinecraft側を選ぶ余地を残す。

主担当者だけが授業外Discord supportを続ける前提にしない。別教師が次を行えることを教材の完成gateにする。

- clean Windows PCから所定時間内に環境を起動する。
- doctor / checklistで典型障害を切り分ける。
- McRemoteが使えない日は同じAPI学習目標をPython-only課題で続ける。
- backup / restart / credential再pairを手順どおり回復する。

### 環境構築の段階的開示

pyenv + Poetryから`uv`へ移し、初回はtemplateと`uv run`で制作へ早く到達させる。ただし環境を永久に隠さない。

1. 導入期: templateをcloneし、用意されたcommandで動かす。
2. API利用期: `pyproject.toml`、dependency、module境界を読む。
3. API公開期: 生徒自身がpackage metadata、dependency、test、example、READMEを所有する。

環境構築を学習から削除するのではなく、最初の楽しさを得る前の関門から、成果を他者へ渡すための意味ある課題へ移す。

### 実施時系列

`2026-07-25-03` でケータリング型の確立を公開 stable 版より上に置いたため、旧「stable 優先・ケータリングは後段 track」の順序は使わない。

- **2026年7〜8月**: ケータリング型（`2026-07-25-04`）の確立を主線に置く。ケータリング型と stable release が競合したときはケータリング型を先に通す。stable release を取り下げるわけではない。
- **2026年8月**: 現学年は卒業発表で終了する。未検証の教室 runtime をここで初投入しない。
- **2026年8月以降**: `classroom-all-in-one` profile、ケータリングキット（PC ・ AP ・ 接続 ・ 電源）、教材、teacher checklist、Python-only fallback を lab と別の支援者で検証する。
- **2027年4月**: 新学年の3年間を開始する。共通 Python 基盤を全体へ、McRemote を選択層へ導入する。

順序を入れ替えても gate は外さない。**別の支援者が授業外の個別支援なしに setup ・ 開始 ・ 復旧できること**を共通基盤の gate として維持する（`2026-07-16-05`）。

現場検証は、既存の専用 AP ・ Internet ・ 施設側 routing が整った対面教室を positive control として使える。まず既存 network 上で `classroom-all-in-one` を検証し、次に USB Wi-Fi AP を含む完全なケータリングキット構成を検証する。学習者名、token、IP、作品の非公開情報を証跡へ残さない（`2026-07-06-03` / `2026-07-21-04`）。

なお home 構成はケータリングキットに当たらない（AP を持たない）。home で成立するのはケータリング型と準備済み deployment までであり、キットの検証は教室構成で別途行う。

## 14. 機能実現の三層モデル

出典: McRemote dev session（`world.setSign`設計対話、2026-08-24〜26）からの文書素材を
`2026-08-26-03`で確定した。技術側の関連契約は
[10-protocol/wire-format-design](../10-protocol/wire-format-design_ja.md) §5.8、no-merge方針は
`2026-08-19-02`。並行実行の教育哲学は §11、3年間カリキュラムのAPI層diagramは §12 を参照する。

### 三層は「どこで実現するか」であり、高級／低級の階段ではない

同じ機能を、次の三つの実現位置に置ける。

1. **server／plugin API層**: Paper pluginがwire methodとして実行し、server上で結果を保証する位置。
   認可、atomicity、共有worldの並行更新、有限work、全client共通の正準意味論を所有できる。
2. **client API層**: Python libraryやScratch extensionが利用者へ公開する位置。単一wire methodの薄い投影も、
   複数methodの合成、型や表現の変換、学習者向けの語彙も置ける。
3. **ユーザーコード層**: コードを書く人がPythonの関数／classやScratchのscript／定義blockとして実現する位置。
   課題固有の手順、実験、再利用部品、学習者自身のAPIを置ける。

三層は排他的な所有区分ではない。**同じ概念が三層すべてに重複して存在してよい**。用意されたScratch blockで
全体像を先に掴み、同じ動作をユーザーコードで組み直し、必要ならclient APIやplugin APIの実装へ進む、という
複数の学習経路を同時に残す。ある層で実現できることは、他の層へ置かない理由にはならない。

この意味で「API三層」とは呼ばない。ユーザーコードは必ずしもAPIではなく、「三層責務」も機能を一層だけへ
割り当てる印象を生む。正称を**機能実現の三層モデル**とし、「責務」は各層が保証すべき性質を述べる時だけ使う。

### 利用者から見える境界

Python利用者に見える`mc.foo()`はclient APIのsurfaceである。その内部が一つのwire methodを委譲しているか、
複数のwire methodをclientで合成しているかは、呼出し表記だけでは分からない。`mc.`の付かない関数やclassは
ユーザーコード、別library、または利用者が作ったAPIのいずれにもなり得る。

Scratchでも、McRemote extensionのblockはclient APIのsurfaceだが、そのblockがpluginへ一回送信するか、
client内で複数操作を合成するかは初学者から見えなくてよい。Scratchの「ブロック定義」や組み合わせたscriptは
ユーザーコード層に当たる。実現位置を観察する必要が生じた段階では、教材説明、source、test、WireScopeを使って
境界を明らかにし、見た目の記法から推測させない。

### 操作の粒度・意味のまとまりは別軸

server／client／ユーザーコードという実現位置と、APIの「細かさ」「人間に近い意味」「複合度」は直交する。
server APIを「原始的」「低級」、client APIやユーザーコードを「高級」とは定義しない。各層に、単一対象の操作、
複数対象の一括操作、Minecraftの目的語彙、教材や作品固有の語彙が混在し得る。

例えば次は配置を考えるための例であり、同名methodの採用を決める表ではない。

| 概念例 | 操作の性格 | 置き得る実現位置 |
| --- | --- | --- |
| `setBlock` | 一地点のworld状態を指定する | pluginへの一回の委譲、client API、直接呼ぶユーザーコード |
| `postToChat` | 一操作だが人間に明確な意味を持つ | plugin＋client API。必要ならユーザー側のmessage helper |
| `updateSign` | 対象固有の一部変更 | atomicityを持つplugin、GET＋PUTを合成するclient、ユーザー関数 |
| `Door.open` | Minecraft対象を目的語彙で扱う | client library、ユーザーclass、必要ならserver側のatomic操作 |
| `buildPyramid` | 多数の配置を一つの目的へ合成する | 教材用client helper、ユーザーコード、有限batchを担うserver操作 |

一つの尺度で高級／低級を付けると、`postToChat`のように一回で完結しながら人間的意味が強い操作や、
`setBlocks`のようにserver APIでありながら多数の変更を束ねる操作を説明できない。設計時は少なくとも、
**実現位置**、**何回・何対象を束ねるか**、**どの利用者概念を名前にするか**を別々に記録する。

### 三層間の関係

- **委譲**: client APIが同じ意味のplugin methodを一回呼ぶ。
- **合成**: client APIまたはユーザーコードが複数操作から新しい意味を作る。
- **併存**: 用意されたAPIがあっても、学習者が同じ機能を自分で再実装できる。
- **昇格**: 繰り返し使う合成をclientまたはpluginへ追加する。便利だから自動昇格するのではなく、必要な保証で決める。

plugin層へ置く主な理由は、serverでのatomicity、認可、共有状態の競合制御、性能・有限性、全client共通の意味、
clientからは安全に実現できないcapabilityである。client層へ置く主な理由は、Python／Scratchごとの自然な表現、
発見しやすさ、定型的な安全な合成、教材上の足場である。ユーザーコードへ置く主な理由は、組み合わせること自体が
学習対象であること、作品固有であること、まだ共通APIへ固定する段階でないことである。複数の理由が成立すれば、
複数層へ置いてよい。

### MCPIは出発点であって上限ではない

Raspberry Pi Edition向けMCPIは、小さいMinecraft APIとPython clientを用意し、その先の組み合わせを
ユーザーコードへ広く委ねた。この簡潔さと、自分で組み立てられる余地はMcRemoteでも重要である。一方、MCPIで
server APIになかったことだけを理由に、client APIやplugin APIへの追加を退けない。`updateBlock`／`modifyBlock`、
対象別操作、教材用の語彙を検討することは、歴史からの逸脱ではなく、現在の並行実行、複数client、観察可能性、
学習経路に合わせて三層の配置を選び直すことである。

### PUTとPATCHという二つの正当なメンタルモデル

- **PUT的操作**: 「これから先、これがこの場所の指定した全体状態である」と宣言する。新しく置く、または
  対象単位を完全に置き換える時に自然。
- **PATCH的操作**: 「今そこにある物の、この点だけを変える」。他の状態を維持して調整する時に自然。

GET＋PUTをclient APIまたはユーザーコードで合成すればPATCH的な体験を作れる。その経路は、学習者が状態の
読み書きを理解する題材にもなる。一方、Scratchの並行scriptなどで複数処理が同じ対象を更新すると、GETからPUTまでに
他の変更を上書きするlost updateが起こり得る。server側PATCHはatomicityと全client共通の意味を持てる。

したがって、PATCHをどの層へ置くかは高級／低級や便利さだけで決めず、学習価値、競合、正準意味論、対象範囲から
決める。`2026-08-19-02`のno-mergeは`BlockSpec`の入力契約を固定した判断であり、別methodとしてのPATCHを永久に
禁止する一般原則ではない。

### 学習経路への投影

学習者には、その時点で理解しやすい入口を提示する。Scratch初学者には用意されたblockから概念全体を見せられる。
Python学習者は`Door.open`を使うことも、`getBlock`＋`setBlock`から自分で書くことも、client libraryへまとめることも
できる。さらに進めばplugin側のatomicityやwire contractを扱える。これは一方向に高級から低級へ降りる階段ではなく、
同じ概念を異なる実現位置から作り直して理解する経路である。

PUTのみ、GET＋PUT、PATCHという提示順は操作意味論の学習候補であり、三層の順序とは別である。`buildPyramid`、
`updateSign`、`postToChat`等の語彙も単一の高級／低級尺度へ並べず、学習目標ごとに入口を選ぶ。

### この節が主張しないこと

- すべての機能を三層へ重複実装することを必須にしない。
- `world.updateBlock`、`world.updateSign`、`Door.open`、`buildPyramid`という具体的APIの採用を確定しない。
- `mc.`の有無を、plugin実装かclient合成かを判定する規則にしない。
- PUT／GET＋PUT／PATCHの順を教材progressionへ自動適用しない。
