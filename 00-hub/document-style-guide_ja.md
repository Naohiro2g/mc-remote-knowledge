# 説明文書の様式ガイド

このガイドは、設計内容そのものではなく、knowledge リポで説明文書を書く順序と拘束の置き場を定める。
文書三層の正本は `2026-08-10-01`、リポ構造全体は
[knowledge repository design](knowledge-repo-design_ja.md) を参照する。

## 1. 三層の役割

| 層 | 主な実体 | 正とする性質 |
| --- | --- | --- |
| 拘束層 | DECISIONS、固定票 template、terms glossary、各 owner の lock／schema／conformance fixture | ID、field、列、参照、検査可能な形式を保ち、解釈なしに適用・照合できる |
| 説明層 | 各スポークの設計文書、knowledge 自己記述 | 人間が「何であるか」「誰が何をするか」から理解できる |
| 投影層 | README、Gemini Notebook 投影、チュートリアル、対象別入口 | 読者と作業に合わせて説明層・拘束層から選び直した入口。独立した正本にしない |

層は directory や file extension だけで判定しない。一つの README が入口と短い説明を持ってもよいが、
新しい拘束を README だけへ置かない。人間が DECISIONS を確認することは妨げないが、拘束層は通読性を
主目的にしない。

## 2. 説明は骨格から始める

説明層の文書は、可能な範囲で次の順に書く。

1. **肯定形の骨格**：何であるか、登場人物、責務、通常の流れを一画面程度で示す。
2. **具体例と配役**：profile や利用場面によって誰が各 role を担うかを示す。
3. **否定形の柵**：してはいけないこと、security boundary、例外、未確定事項を示す。
4. **拘束層への錨**：柵を支える DECISIONS、glossary、schema、fixture へリンクする。

アナロジーは骨格を理解する入口として使える。ただし、アナロジーだけから新しい実装責務や権限を導かない。

## 3. 散文だけに拘束を住まわせない

説明文書に禁止・必須・field・lifecycle・capability 境界を書くときは、対応する拘束層を確認する。

不要な禁止ルールを作らない。誤りと判明したルールは、元の判断履歴を消さずに撤回／改訂先を接続した上で、
現行の説明、runbook、schema、fixture、validationから除く（`2026-09-04-05`）。

- 既に拘束層にある場合：完全 ID、section、schema／fixture 名を参照する。
- 新しい横断判断である場合：人間レビュー後に DECISIONS へ置く。
- 局所 contract である場合：owner の schema、fixture、不変条件節等へ置く。
- まだ確定できない場合：説明文書で確定形にせず NOTES または未確定節へ送る。

標語は **「文書は説明し、台帳が拘束する」** とする。

## 4. 漸進適用

既存文書を一括で書き直さない。スポーク文書へ意味変更を加える機会に、次を同じ作業範囲で確認する。

1. 冒頭に肯定形の骨格があるか。
2. 後続の柵が拘束層へ錨を持つか。
3. README やチュートリアルが独立した第二の正本になっていないか。
4. 説明と拘束が食い違う場合、散文へ規則を足して隠さず正本側へ戻して判断する。

最初の適用例は [WireScope](../15-wirescope/README_ja.md) の source／station／browser 三役モデルとする。
